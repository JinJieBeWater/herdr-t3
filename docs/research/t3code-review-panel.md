# T3 Code Review / Diff 面板调研

## T3 Code 的模型

T3 Code 把 diff 当作线程工作区的一个可切换右侧 surface：同一个面板能看当前 branch Changes、Uncommitted、Latest turn、单个 turn、commit 和 tool-call diff；PR 则是另一条完整的详情与正式 review 流程。工作区行批注会进入聊天 composer 的 `reviewComments` 上下文，PR 行批注则能加入正式 PR review，或立刻 handoff 给 agent。DiffPanel 提供文件导航和阅读方式；GitActionsControl 是相邻但独立的线程控件，负责 stage/commit/push/PR。源码证据与路径行号汇总在 [Subject A 证据](t3code-review-panel-subject-a.md)；clone HEAD 为 `09a54f01bc0ae83865347a965ced50f8c8ec2953`（2026-11-08），干净工作区，详见该证据文件第 3 行。

## 建议向用户确认的设计问题

这些是会改变产品行为的决策。建议默认答案先供 lead 与用户讨论，确认前不把它们当作隐含需求。

1. **新的 Review 页面是否继续只围绕 `jin.review` 评审，还是把 T3 的通用 diff scope 一并合并？** 建议：保留 Review 的 AI 分组与 `jin.review` 为主流程，只吸收 Files / Changes 的导航交互；通过 bar/commit picker 明确表示 worktree、branch、commit scope。理由：T3 的 thread-turn/tool-call scope 无法由 Herdr 当前模型自然提供；合并会扩大页面的数据源和状态机。
2. **是否需要行批注并交给当前 agent？** 建议：先做只读定位与 reviewed 流程；若用户确认 handoff 是主要用例，再设计明确的 target agent 选择与 file/line context 传递。理由：当前只有 AI 评审 notes 与 `review.reveal` 文件定位；T3 的 composer/comment context 在 Herdr 没有同构 API，fork 计划也把 Chat 列为 out of scope。
3. **是否要在此页内完成 GitHub PR review（inline comment、Approve、Request changes）？** 建议：先不将 PR 写入动作塞进本轮 Review 页面重设计；单独定义 GitHub provider、登录方式、草稿保存和失败恢复，再实现。理由：这是与本地 Git diff / AI 分组不同的后端和权限生命周期，目前 fork plan 明确未覆盖。
4. **Review 是否要包含 stage / commit / push / Create PR 操作？** 建议：将只读 Review 和工作区 Git actions 保持区分，除非用户明确希望 Review 成为 Git 操作面板。理由：T3 的 `GitActionsControl` 在 DiffPanel 以外；Herdr Review 对 Git 只读，动作合并会引入写操作和提交状态管理。
5. **窄面板里优先保留哪些导航？** 建议：优先保留 Review scope/commit 标识、Analyze 状态、groups tabs 和 reviewed 状态；宽度不足时隐藏/折叠文件 aside 与次要 toolbar 选项，split 自动 unified。理由：Herdr 已有 640/1024px 两级退化策略；AI 状态与组/文件关系是它相对 T3 的差异能力。
6. **是否把 T3 的 wrap 与 ignore-whitespace 作为 Review 的持久偏好？** 建议：先维持现有 split / tree-list / group-nav 偏好，暂缓新增两项，除非对长行或格式化 diff 的需求明确。理由：当前 daemon 返回按需高亮的行，mod 自绘布局；ignore whitespace 需要 daemon/read API 对 diff 计算结果达成语义，不只是 toggle 样式。
