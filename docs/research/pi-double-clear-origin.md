# 两层清理为何重叠：普通屏与全屏渲染器的演变

研究日期：2026-11-12。时间按北京时间（UTC+8）。只读核对上游源码、提交和公开讨论，没有运行旧版 Pi 或修改产品代码。图片缓存回归的后续历史见 [引入与修复时间线](pi-image-clear-history.md)。

## 结论

能追到的结构原因是：**旧普通屏的“完整重建”和“逐行更新”分处互斥路径；新全屏渲染器用同一个行循环处理两种更新，却仍在完整重绘时先做整屏清除。** 这使原本分开的两种清理在完整重绘的一帧内同时执行。

旧策略各有用途：完整重建要重写终端中的文档，逐行更新要擦掉旧行剩余文字；逐行擦除的一次改动还明确针对 xterm.js 闪烁。新全屏实现中两层清理对文字重叠，最初图片每次重传，尚未造成缓存 ID 失效。后来引入图片复用，未同步调整清屏行为，也未在新增测试里覆盖完整重绘组合。

以上能用代码和测试直接证明。**没有找到作者解释“为何在新全屏循环已覆盖每行后，仍必须保留整屏清除”的记录**，不能据此编造复制粘贴、出于防御或赶工等个人动机。

## 1. 旧普通屏：两种清理原本不重叠

核对版本：[新增全屏之前的 `tui.ts`](https://github.com/earendil-works/pi/blob/96eda8b47f01dd795ee5b8633c253db1e903ba0c/packages/tui/src/tui.ts)。

```text
完整重建：清屏 + 清回滚历史 → 重新打印全文 → 返回
局部更新：定位到变化行     → 擦该行、写该行
```

- [`fullRender(true)`，1288–1311 行](https://github.com/earendil-works/pi/blob/96eda8b47f01dd795ee5b8633c253db1e903ba0c/packages/tui/src/tui.ts#L1288-L1311)：发 `CSI 2J`、光标归位、`CSI 3J`，随后逐行打印内容，循环里没有显式 `CSI 2K`。
- [增量路径，1468–1524 行](https://github.com/earendil-works/pi/blob/96eda8b47f01dd795ee5b8633c253db1e903ba0c/packages/tui/src/tui.ts#L1468-L1524)：仅在没有进入完整重建时执行，用 `CSI 2K` 擦行后覆盖。完整重建的分支会提前 `return`。

`2J` 清当前画面，`3J` 清回滚历史，二者不能混称。旧普通屏依靠终端历史承载长文档；当已滚出视口的内容发生变化时，不能直接按屏幕坐标更新它，代码选择清除后重新打印。清除旧历史也防止旧文档与重印的新文档同时留在终端中；这是从行为推导出的作用，不等于作者曾逐字写下这项动机。

可查到的历史依据：

| 改动 | 直接证据 |
| --- | --- |
| [2025-11-12 `fb4893d8d4`](https://github.com/earendil-works/pi/commit/fb4893d8d4) | 标题为 `Clear scrollback buffer on full TUI re-renders`，给全量重建补上 `CSI 3J`。不是首次出现 `3J`，更早版本也用过。 |
| [2025-11-19 `1b28780155`](https://github.com/earendil-works/pi/commit/1b287801550fb7a4e4817854e856689b121a2edb) | 将增量路径的整段 `CSI J` 改为逐行 `CSI 2K`，注释明确说是避开 xterm.js 的 clear-to-end 闪烁。此改动并非 `2K` 在整个项目中的首次使用。 |
| [2026-03-14 `fa26f15e68` / #2155](https://github.com/earendil-works/pi/commit/fa26f15e689bda17019f82236db7fe6e22e634ce) | 将顺序改成先 `2J` 再 `3J`。提交解释其遇到的清屏行为会把旧屏内容推进回滚区，因此应最后再清历史；这是该次修复的实现依据，不是所有终端的通用协议保证。 |

逐行擦除还有直观作用：把 `abcdef` 改成 `ok` 时，仅覆盖开头会留下 `okcdef`；先擦行即可去掉旧尾巴。

## 2. 为什么另写全屏渲染器

[#7304](https://github.com/earendil-works/pi/issues/7304) 是这次架构变化的公开需求：2026-07-30，用户报告在 Windows Terminal 中上翻阅读流式输出时，Markdown 重排改变了已滚出视口的行，触发 `firstChanged < prevViewportTop` → `fullRender(true)` → 清回滚历史，阅读位置随之跳动。

维护者先回复 Markdown 重排、工具框背景变化都可能触发此问题；随后于当日加入实验性全屏渲染器，并[公开说明](https://github.com/earendil-works/pi/issues/7304#issuecomment-5130004151)由应用自己管理视口，以便内容在上方变化时仍保留手动滚动位置。

对应提交：[Mario Zechner，2026-07-30，`c13ffe1877`](https://github.com/earendil-works/pi/commit/c13ffe1877c3a47ce9f2fc98d9880447d64a0e87)。旧逻辑基本移入 `TuiMainScreen`，另写 `TuiAltScreen`；两种渲染器各有 `doRender()`，并不共享绘制循环。

## 3. 重叠发生的具体连接点

新全屏渲染器不再把整个文档作为终端滚动流输出，而是取当前视口的内容切片，按绝对行号更新。它没有旧的 `firstChanged < prevViewportTop` 清历史分支，也不发送该分支的 `CSI 3J`。

但其[最初绘制代码，398–415 行](https://github.com/earendil-works/pi/blob/c13ffe1877c3a47ce9f2fc98d9880447d64a0e87/packages/tui/src/TuiAltScreen.ts#L398-L415)是：

```text
完整重绘：先 CSI 2J ─┐
                    ├→ 同一个行循环：定位、CSI 2K、写内容
局部刷新：──────────┘                 （局部时跳过未变行）
```

所以从新增全屏实现的第一版起，完整重绘就同时做整屏与逐行清理。**这是新全屏内部的重叠，不是普通屏和全屏之间共享循环。** 两种旧策略与新代码存在结构对应，但没有证据证明作者采用了某种具体复制或迁移操作。

当时未找到说明这一分支仍须整屏清除的注释、文档或测试。这个“未找到”不能证明作者完全没有考虑过；能确定的是，逐行循环已覆盖完整文字视口，而最初仍会重新上传图片，因此没有此次缓存失效的后果。

## 4. 为什么缓存优化没有挡住这个组合

[2026-08-02 的 `73414d08`](https://github.com/earendil-works/pi/commit/73414d08b94d7db46d3fa66582c8fe3b02dabf72)为减少传输，新增已上传图片缓存：重绘时改用 `a=p` 引用旧 ID，但完整重绘前的 `CSI 2J` 仍在。

同次提交新增的 `reuses moved Kitty images without dropping HStack siblings` 测试改变 header 和 label，使图片位置变化，然后检查：

- 出现 `a=p`，没有重新发送 `a=T`；
- 重绘输出小于 2000 字节；
- 相邻文字仍然显示。

它没有调整终端尺寸，也没有测试完整重绘后终端是否还保存图片数据。测试记录输出字符串，不模拟 ED2 回收图片。因此测试证明了优化确实减少传输，但没有覆盖“完整重绘清屏 + 图片 ID 复用”的组合。

## 5. 最终修复怎样验证了这份冗余

[2026-11-11 的修复 #12047](https://github.com/earendil-works/pi/pull/12047)明确解释：每一行已经用 EL2 清理，因此有 Kitty 图片缓存时跳过整屏清除，保留数据并重新放置图片。

这项判断针对该缓存分支；它没有删除所有协议、所有场景里的整屏清除。新增回归测试则覆盖 resize 后的完整重绘，并断言仍有 `a=p`、没有 `a=T`、没有 `CSI 2J`。

可以确认的因果链是：**旧架构中的两条互斥清理路径 → 新全屏内部采用共同逐行循环，同时保留整屏前缀 → 图片缓存优化没有同步处理清屏副作用，测试也未覆盖该组合 → 最终在保留缓存的分支去掉整屏清除。**

本次没有运行旧版本或推测作者个人动机，没有对上游发消息。现有 Herdr / Ghostty 的运行证据另见协议研究；此处新增证据全部来自历史源码、注释、测试和公开讨论。
